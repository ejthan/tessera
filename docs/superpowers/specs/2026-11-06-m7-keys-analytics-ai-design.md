## 4. tessera-client

New modules `keys.rs`, `analytics.rs`, `stemming.rs`, `models_ai.rs`. Bodies stay JSON where a server may add fields.

### 4.1 Keys (`keys.rs`)

```rust
pub struct ApiKey {          // Deserialize
    pub id: u64,
    pub description: String, // default ""
    pub actions: Vec<String>,
    pub collections: Vec<String>,
    pub expires_at: Option<i64>,
    pub value_prefix: Option<String>,
    #[serde(flatten)] pub extra: Map<String, Value>,
}
pub struct NewKey { pub description: String, pub actions: Vec<String>, pub collections: Vec<String>, pub expires_at: Option<i64> }
pub struct CreatedKey { pub key: ApiKey, pub value: SecretString }
```

| Method | Endpoint | Behaviour (both) |
|---|---|---|
| `keys()` | `GET /keys` | `{"keys":[…]}`. `value_prefix` is the first 4 characters. A key without expiry reports `expires_at: 64723363199` |
| `key(id)` | `GET /keys/{id}` | 404 `Not found.`. A path that is no integer gets no answer at all, so only `u64` ids reach the path |
| `create_key(&NewKey)` | `POST /keys` | 201, the only answer with `value`, in place of `value_prefix` |
| `delete_key(id)` | `DELETE /keys/{id}` | `{"id":n}`, 404 when gone |

`create_key` runs on `self.without_response_bodies()`, inside the client, so no caller can put the value in the log. `CreatedKey` takes `value` out of the JSON into a `SecretString` before anything else sees it; its derived `Debug` prints the secret as redacted. `raw()` does the same for a `POST` to `keys`, because the console's masked display (D41) is not enough for "never logged" (§7.14): the event would still hold the value in memory, and "Copy" paths read it. The console itself still gets the answer.

`Client::with_key(&self, key: SecretString) -> Self` returns a clone using another key, for the scoped key test. The clone shares nodes, hook and flags; the event's `key_prefix` is then four characters of a base64 digest, which tells nothing.

### 4.2 What the server enforces (traps)

- **Any action string is accepted, and many documented ones do nothing.** `POST /keys` takes `nope:x`. Each request was tried with a key holding only that action, on both versions. The rule the server follows is `<path without ids>:<verb>`, with `GET` list = `list`, `GET` one = `get`, `POST` = `create`, `PUT` = `upsert`, `DELETE` = `delete`. So:

  | Docs say | Server refuses (401) | Works |
  |---|---|---|
  | `aliases:create` | yes | `aliases:upsert` |
  | `synonym_sets:create` | yes | `synonym_sets:upsert` |
  | `stopwords:create` | yes | `stopwords:upsert` |
  | `analytics:list`, `:get`, `:create`, `:delete`, `:*` | all, on every analytics route tried | `analytics/rules:*` and its verbs, `analytics/events:create`, `analytics/events:list`, `analytics/status:list`, `analytics/flush:create` |
  | `stemming/dictionaries:create` | yes, also `:*` | `stemming/dictionaries/import:create` |
  | `operations/schema_changes:get` | yes | `operations/schema_changes:list` |

  `curation_sets:upsert`, `presets:upsert`, `conversations/models:upsert`, `nl_search_models:upsert`, `collections:update`, `analytics/rules:upsert` work as named. The form offers the measured names (D70, §5.3).
- **`expires_at` in the past is accepted** and makes a key that never works. The form refuses it.
- **A scoped key needs a parent with exactly one action, `documents:search`.** Parents with `*`, `documents:*` or `documents:search` plus another action answer 401, as does the bootstrap key, and a parent shorter than 4 characters. A non-ASCII parent answers 401 too: the server takes four bytes and the libraries four characters. Every 401 is the same message, `Forbidden - a valid x-typesense-api-key header must be sent.`, so the panel explains it (D71).
- **Scoped keys:** the embedded `filter_by` is ANDed with the client's (a client filter against it gives 0 hits). Other embedded parameters win over the client's (`per_page`). Only search answers: `GET /collections/c`, `GET …/documents/1` and `GET /keys` are 401. `expires_at` must be a JSON integer: a string or float is 401. A later `expires_at` than the parent's does not help: the key dies with its parent. An array where the server wants a string (`query_by`) gives 400 `Error applying search parameters inside Scoped Search API key`, which is why the libraries join arrays. Whitespace in the JSON is accepted. Base64 without padding is accepted. `limit_multi_searches` works. Two parents with the same 4-character prefix both work.

### 4.3 Analytics (`analytics.rs`)

Rules stay `Map<String, Value>`.

| Method | Endpoint | Behaviour (both) |
|---|---|---|
| `analytics_rules()` | `GET /analytics/rules` | Bare array. `rule_tag` is `""` when unset, `params` may be missing or `null` |
| `analytics_rule(name)` | `GET /analytics/rules/{name}` | Unknown: **400** `Rule not found`, not 404 |
| `create_analytics_rule(&Value)` | `POST /analytics/rules` | 200, not 201. A duplicate name: 400 `Rule already exists`. An array body answers one item per rule, errors inside a 200, so Tessera sends one object |
| `update_analytics_rule(name, &Value)` | `PUT /analytics/rules/{name}` | **Upsert:** an unknown name creates a rule. A partial body merges, also inside `params`. `name` in the body is ignored. A changed `type`: 400 `Rule type cannot be changed` |
| `delete_analytics_rule(name)` | `DELETE /analytics/rules/{name}` | Answers the rule. Unknown: 400 |
| `analytics_event(&Value)` | `POST /analytics/events` | `{"ok":true}` |
| `flush_analytics()` | `POST /analytics/flush` | `{"ok":true}`, and the aggregates reach the destination within seconds, whatever the interval (both, with interval 3600) |

Validation seen: `Destination collection does not exist`, `Destination collection is required when creating a no hit queries or popular queries type rule`, `Event type or type is invalid (or) combination of both is invalid`, `Counter field is required when creating a counter type rule`, `Collection c does not exist`. `popular_queries` and `nohits_queries` take `search`. `counter` takes `click`, also `conversion` and `visit` per the docs. `log` took `click`, `conversion`, `visit` and `search`.

Traps:

- **No endpoint says whether analytics runs.** See §4.4.
- **Deleting a source or destination collection leaves the rule.** It stays listed and deletable.
- **An event whose `event_type` differs from the rule's is accepted and counted** (a `conversion` on a `click` counter added its weight). The form sends the rule's type.
- **`POST /analytics/events` is limited to 5 requests per minute by default**, and refused ones count: the sixth answers **500** `event rate limit reached.`. The help text says the default of `--analytics-minute-rate-limit` is 0, which is wrong. With the flag at 1000, eight in a row passed (both).
- A log or counter event needs `doc_id` or `doc_ids`, else 400 `doc_ids or doc_id is required`. A popular query event takes `q`: this is the one way to feed a rule without waiting out the 4-second debounce on searches.

### 4.4 What starts analytics

The docs name two flags: `--enable-search-analytics=true` and `--analytics-dir`. The dev server has neither. On a server without them, rules, events and flush all answer as on a working one, and `status` shows the buffer filling. Measured on 30.2, rule plus event plus flush:

| Flags | Rules, events answer | Popular queries reach the destination | Log events survive a flush |
|---|---|---|---|
| none (dev server) | normally | no | no |
| `--enable-search-analytics=true` only | normally | no | no |
| `--analytics-dir` only | normally | no | yes |
| both | normally | yes (both versions) | yes |

`--analytics-flush-interval` defaults to 3600 s. The docs state a minimum of 60, but 5 and 3600 both ran. All flags also work as environment variables (`TYPESENSE_ENABLE_SEARCH_ANALYTICS`, `TYPESENSE_ANALYTICS_DIR`, `TYPESENSE_ANALYTICS_FLUSH_INTERVAL`, `TYPESENSE_ANALYTICS_MINUTE_RATE_LIMIT`; both versions), which is what CI's service container needs.

Since a client cannot detect this, the analytics view always shows the two flags as a notice (D73). `dev/docker-compose.yml` and CI gain them.

### 4.5 Stemming (`stemming.rs`)

| Method | Endpoint | Behaviour (both) |
|---|---|---|
| `stemming_dictionaries()` | `GET /stemming/dictionaries` | `{"dictionaries":["id",…]}`: names only |
| `stemming_dictionary(id)` | `GET /stemming/dictionaries/{id}` | `{"id":…,"words":[{"word":…,"root":…}]}`. Unknown: 404 `Collection not found` (sic) |
| `import_stemming(id, jsonl: &str)` | `POST /stemming/dictionaries/import?id=` | 200 echoing the lines, `Content-Type: text/plain`. `id` is percent-encoded with `encode_query` |
| `delete_stemming(id)` | `DELETE /stemming/dictionaries/{id}` | `{"id":…}`, **200 also for an unknown id**. Not in the vendored OpenAPI file, in the docs and on both servers |

Traps:

- **An import merges into an existing dictionary, and a word keeps the root it has.** New words are added. A word already there stays as it is, whatever root the file gives it, and the first of a word repeated in one import wins. All of this was measured on 30.0 and 30.2. A changed root needs a delete and a re-import.
- **A bad line stops the import after the lines before it were stored.** `{"word":"a","root":"b"}\nnot json` answers 400 `Invalid dictionary format.` and the dictionary exists with `a`. A line without `root`: 400 `dictionary lines should contain word and root values.`. `word: 5`: 400 `Bad request.`. So the file is validated first and whole (§5.5).
- **The server stores what it gets:** case, spaces, an empty `word`, and it drops unknown keys. An empty `id=` is accepted too.
- **A deleted dictionary leaves collections working.** Search and writes on a collection whose field names it still answer 200. `stem_dictionary: "nope"` at collection create is also accepted, so nothing warns. The delete dialog names the collections that use it.
- The body goes through `import_batch`'s raw route: `self.without_bodies()`, because a dictionary can be large, with `LONG_TIMEOUT`.

### 4.6 AI models (`models_ai.rs`)

Conversation models and NL search models share their shape, so one module serves both, as `sets.rs` does (D77).

```rust
pub enum ModelKind { Conversation, NlSearch }  // path(): "conversations/models", "nl_search_models"
impl Client {
    pub async fn ai_models(&self, kind: ModelKind) -> Result<Vec<Map<String, Value>>, Error>;  // bare array
    pub async fn ai_model(&self, kind: ModelKind, id: &str) -> Result<Map<String, Value>, Error>;
    pub async fn create_ai_model(&self, kind: ModelKind, body: &Value) -> Result<Map<String, Value>, Error>;
    pub async fn update_ai_model(&self, kind: ModelKind, id: &str, body: &Value) -> Result<Map<String, Value>, Error>;
    pub async fn delete_ai_model(&self, kind: ModelKind, id: &str) -> Result<(), Error>;
    pub async fn ai_search(&self, collection: &str, params: &[(String, String)]) -> Result<String, Error>;
}
```

Every model call runs on `self.without_bodies()`: a create carries the provider key, and a read carries its first five characters. Create and update use `AI_TIMEOUT = 120 s`, because the server calls the provider before it answers (the profile default is 5 s). `ai_search` is a `GET` with an explicit timeout of `AI_TIMEOUT`, so a timeout is not retried: a retry would call the LLM again and store the turn twice.

Traps (both, unless noted):

- **A `PUT` stores whatever `api_key` it gets, including a mask.** `{"api_key":"sk-st***"}` replaced the real key and answered 200. Lists and reads answer `api_key` masked as `sk-st*********`. So an edit must never echo what it read (D77).
- **`PUT` merges:** `{"system_prompt":"changed"}` keeps the rest. An unknown id: 404 `Model not found`, so there is no accidental upsert. `POST` with an existing id: 409 `Model already exists`. No `id`: a UUID is generated.
- **Create calls the provider.** A fake key on `openai/gpt-4o` answers 400 `OpenAI API error: Incorrect API key provided: sk-fake. …`: the provider's message, which can echo the key (D77). Without a provider, nothing can be created except through `openai_url` or `api_url`.
- Conversation validation: `Property history_collection is missing or is not a string.`, `Schema is missing conversation_id field`, `Collection not found`, `Property max_bytes is not provided or not a positive integer.` (also on `PUT`), `API key is not provided`, `Model namespace nope is not supported.`.
- NL validation: `Property model_name is not provided or not a string.`, `Property max_bytes is not provided or not a positive integer.`. `max_bytes` is checked before the namespace.
- **A masked key is still accepted by a lenient provider.** A collection's `embed.model_config.api_key` reads as `sk-st*********`, and a create with that string answers 201 against a provider that ignores it. M2's blanking of clones stays necessary.
- **`nl_query` falls back silently.** An unknown `nl_model_id` answers **200** with a plain search of the sentence and no `parsed_nl_query`. When the LLM fails, the docs promise an `error` field. The panel must treat a missing `parsed_nl_query` as failure (§7.6).
- `conversation=true` with an unknown model: 400 `Model not found`. Same with `conversation_id=nope` while the model is unknown. The answer holds `conversation.answer`, `conversation.conversation_id` and `conversation.conversation_history`. The history collection receives one document per message.
- `POST /multi_search?conversation=true&…` answers `conversation` at the top level. `Client::search` unwraps `results[0]` and would lose it, so a chat stays below the 4,000-byte `GET` limit (§7.6).
- **`query_by` naming a plain vector field:** 400 on 30.2, `Vector field e is not an auto-embedding field…`; **30.0 gives no answer** within 25 s when combined with `conversation=true`. The panel only offers text fields and auto-embedding fields.
- A deleted conversation model leaves its history documents in the history collection.

**Embedding fields** (both): `embed.model_config` takes `model_name`, `api_key`, `url`, and the other keys of the vendored OpenAPI file. `ts/all-MiniLM-L12-v2` took 9.6 s on first use, which downloads it, and sets `num_dim` 384. `ts/nope`: **404** `Model not found`. `openai/text-embedding-3-small` with `url` set to the stub created the field and embedded a document; `num_dim` came from the stub's answer. A fake key answers 400 with the provider's message. `embed.from` naming an unknown field: 400 `Property embed.from can only refer to string, string array or image…`.

Two changes follow in `collections.rs`. A create or `PATCH` whose JSON has a field with `embed` runs on `without_bodies()`, because the body can hold a provider key, and with `LONG_TIMEOUT`, because a built-in model downloads and a remote one is called. `create_collection` otherwise has only the 5-second default.

## 5. tessera-core

No GPUI. Everything here is unit tested. New: `keys/mod.rs`, `keys/scoped.rs`, `keys/actions.rs`, `analytics.rs`, `stemming.rs`, `ai.rs`. Dependencies: `hmac`, `sha2`, `base64` (§10). Time goes through the `jiff` the crate already has.

### 5.1 The algorithm, verified

Read in `src/Typesense/Keys.ts` of `typesense` 3.2.0 and run from a scratch directory. §7.14's formula holds, with three things it does not say:

```
params = normalize(input)                       // arrayable arrays joined by ","
text   = JSON.stringify(params)
digest = base64(HMAC-SHA256(key = parent, msg = text))    // 44 ASCII characters
scoped = base64(digest + parent.substr(0, 4) + text)
```

1. **`digest` is the base64 text, not the 32 bytes**, so the decoded key starts with 44 ASCII characters, then 4 of prefix, then the JSON.
2. **`normalizeArrayableParams` joins arrays with commas** for exactly these 16 names: `query_by`, `query_by_weights`, `facet_by`, `group_by`, `include_fields`, `exclude_fields`, `highlight_fields`, `highlight_full_fields`, `pinned_hits`, `hidden_hits`, `infix`, `override_tags`, `num_typos`, `prefix`, `synonym_sets`, `sort_by`. An array under any other key stays. This is also why the server does not choke on `query_by`.
3. **`JSON.stringify` decides the bytes**: keys in insertion order, no whitespace, numbers in JavaScript's form.

`typesense-js` has no decoder. Tessera's decoder follows from the layout.

### 5.2 Scoped keys (`keys/scoped.rs`)

```rust
pub enum ScopedError { NotAnObject, Parent(ParentProblem), Number, IndexKey, ArrayItem(String), ExpiresAt }
pub enum ParentProblem { Short, NotAscii }
pub fn canonical_params(input: &Value) -> Result<String, ScopedError>;
pub fn generate(parent: &str, params: &Value) -> Result<String, ScopedError>;

pub struct DecodedKey { pub digest: String, pub prefix: String, pub text: String, pub params: Value, pub expires_at: Option<i64> }
pub enum DecodeError { Base64, TooShort, NotUtf8, NotJson }
pub fn decode(scoped: &str) -> Result<DecodedKey, DecodeError>;
impl DecodedKey { pub fn verify(&self, parent: &str) -> bool; }
```

`canonical_params` walks the value and writes JSON text itself, using `serde_json` only for strings: serde's string escapes match `JSON.stringify` (vector 7), and `preserve_order` keeps insertion order. A repeated key keeps its first place and last value in both (vector 8).

Rust and JavaScript differ on numbers only, and rather than reimplement ECMAScript number printing, the writer accepts what both print the same and refuses the rest (D69):

- An integer with `|n| ≤ 2^53 - 1` prints as is.
- A float that is finite and is 0 or has `1e-6 ≤ |x| < 1e21` prints with Rust's `{}`, which is shortest round-trip without exponent: `1000.0` → `1000`, `-0.0` → must be `0`, handled explicitly.
- Anything else is `ScopedError::Number`.
- An object key that is a canonical array index (`"1"`) is `ScopedError::IndexKey`, because JavaScript moves such keys to the front.
- An arrayable array holding anything but strings, numbers and booleans is `ScopedError::ArrayItem(name)`. JavaScript's `join` would write `""` or `[object Object]`.
- `expires_at` that is not an integer is `ScopedError::ExpiresAt`: the server answers 401 to it.
- The top level must be an object.

`generate` refuses a parent under 4 bytes or with non-ASCII characters: the server rejects both, and the JavaScript and Rust prefixes differ for non-ASCII. It uses `Hmac<Sha256>` from the pinned crates and `base64::engine::general_purpose::STANDARD`.

`decode` uses `STANDARD_PAD_INDIFFERENT`, since the server takes unpadded keys. It splits at bytes 44 and 48 of the decoded bytes, which must leave at least 2 bytes of JSON, and parses the rest. `verify` recomputes over the exact `text`, not a canonicalized copy, compares through `Mac::verify_slice` on the decoded digest, and also requires `prefix` to equal the parent's first 4 bytes. A key made by any library verifies, whatever its JSON looks like.

**Fixed vectors**, generated by the real function from `JSON.parse(input)`, and re-derived by a second implementation in Python. The parents are made up. These go into `crates/tessera-core/tests/fixtures/scoped_keys.json`, with `tests/scoped_keys.rs` reading them; the plan's Task 2 has the file in full.

| # | Covers |
|---|---|
| 1 | empty object, 8-character parent |
| 2 | `filter_by`, `expires_at` |
| 3 | input whitespace dropped, `query_by` array joined, order kept |
| 4 | UTF-8, emoji, escaped quote, backslash, newline, tab |
| 5 | `sort_by`, `num_typos`, `prefix` arrays joined; `1.5`, `1000.0`, `-0.0`, `1e3`; nested object with an array and `null` left alone |
| 6 | `query_by_weights` with a float, a non-arrayable array left alone |
| 7 | U+2028, U+007F, control characters, `/<>&` |
| 8 | repeated key, 4-character parent |

### 5.4 Analytics (`analytics.rs`)

### 5.5 Stemming (`stemming.rs`)

```rust
pub const STEMMING_FILE_LIMIT: usize = SET_FILE_LIMIT;   // 16 MiB
pub struct WordRoot { pub word: String, pub root: String }
pub struct BadLine { pub line: usize, pub problem: LineProblem }
pub enum LineProblem { NotJson, NotObject, MissingWord, MissingRoot, NotText, Empty }
pub fn parse_dictionary(text: &str) -> Result<Vec<WordRoot>, Vec<BadLine>>;   // at most 100 BadLine
pub fn to_jsonl(words: &[WordRoot]) -> String;
pub struct ImportCheck { pub sent: usize, pub missing: Vec<String>, pub kept_root: usize }
pub fn check_import(before: &[WordRoot], sent: &[WordRoot], stored: &[WordRoot]) -> ImportCheck;
pub fn collections_using(collections: &[Collection], id: &str) -> Vec<String>;
```

`parse_dictionary` refuses the file at any bad line, blank lines skipped. An empty `word` or `root` is refused here, though the server would store it. Duplicates in a file stay, and the first wins as on the server. `kept_root` counts words of `before` that were sent with another root and keep the one they have: that is the merge the user should hear about. `missing` compares a word of `before` with the root it had, and any other word with the first root sent.

`endpoint_key`: `Conversation` maps namespace `openai/` to `openai_url`, `azure/` to `url`, `vllm/` to `vllm_url`; `NlSearch` maps `openai/`, `vllm/` to `api_url`, `azure/` to `url`; anything else `None`, and the form hides the field. The namespace is what `model_name` holds before the first `/`.

`update_body` (D77) sends only keys whose value changed against `stored`, never a key in `AI_SECRET_KEYS` from `more`, and `api_key` only when the user typed one. `set_embedding` writes `embed` as a `Value`, keeping unknown keys of an existing `embed` and writing `api_key` only when `Some`, and clears `num_dim`.

## 13. Risks

- **The action table is measured, not documented.** A later server could honour the documented names. The catalog is one constant, and the live test `actions_in_the_catalog_grant_what_they_say` probes each resource's list action, so a change fails CI.
- **Docs and server disagree on rate limits and flush minimum.** Both were measured on 30.0 and 30.2 only.
- **`ts/e5-small` was not probed;** only `ts/all-MiniLM-L12-v2` was. The docs name both. A wrong name in the completion costs the user a 404 inline, nothing else.
- **`openai_path`, Azure `url`, `cloudflare/` and `vllm/`** come from the docs and were not run. They pass through `more` or `endpoint_key`, and the server's message shows if a key is wrong.
- **The stub proves Tessera's side only.** A real provider's error shapes pass through as text, which is the point of UX rule 2, but `nl_outcome` was fed only stub answers and the docs' examples.
- **The running dev server has analytics off until recreated.** Tests stay safe, §8.2.
- **`POST /keys` in the raw console:** the fix keeps the value out of the log entry, so "Copy as curl" of that entry has no response. That is the intent.
- **Reveal and the clipboard:** Copy puts the key on the OS clipboard, where Tessera cannot protect it. §7.14 asks for the button.
